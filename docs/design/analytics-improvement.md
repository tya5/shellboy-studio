# Analytics improvement (#147): design for review

## Non-goals

- Step 1 is this document only: no mock, code, dependency, Core issue, or change to the existing screen. Show a mock before building, and get user approval for anything original beyond the cited patterns.
- No new Core features, prices, currency, guessed savings, inferred provider activity, or estimates. Existing reader-weighted effective tokens are a labeled local index, not measured tokens or money. Do not promote that index into a measured headline.
- No chart that requires unbounded reads, client-side history mining, a new ledger, polling, or a browser fan-out over Threads, models, or turns. Do not turn resource diagnostics into usage history or change their actions.

## First path to mock, after approval

**Overview > 24 hours > select the previous-period comparison > tap an hour > see its Threads > open a Conversation.** The first screen shows the active time zone and bounds, a single request-count comparison, and one hourly chart. On selection, a titled region shows that hour's ranked contributing Threads and exact values. A separate native link opens an available Conversation by Thread ID; it does not claim to scroll to that hour. Returning shows the same period, hour, scroll, and focus. Keyboard users can reach the identical action from the chart's value table. Mock this path with synthetic facts on desktop and a 390 CSS px viewport, in shipped light and dark themes. Include complete, partial/unknown, an absent prior bucket, two clipped edges, a high-volume hour with Continue, and an unavailable Conversation link. Do not mock every tab first.

Core grouped usage uses half-open RFC3339 bounds `[since, until)` (default last 24 hours, maximum 31 elapsed days); attempts use saved start, not completion or prorated overlap. `hour`, `day`, `thread`, `model` and separately `shell-exit` are supported by Core; current Studio wire type exposes the first four. Core allows one explicit Thread/Run/Turn scope, with bounded descendants when scoped to a Thread. Default grouped scope excludes deleted Threads. Per candidate window: at most 10,000 attempt candidates (plus lookahead) and, where applicable, a separately bounded compaction metadata scan (10,000 rows, 4 MiB page budget). At most 168 group rows per response; cursor pages remaining groups then the next candidate window. Groups recur across windows; the cursor carries an insertion watermark, not an atomic snapshot across walks. Studio stops after 64 response reads per run of a walk, offers explicit Continue, and stops a large group map at its 2,000-group threshold at a page boundary when more remains. Coverage (excluded starts, malformed/unknown-time compactions, truncation, cancellation and scope limits) must travel with the result. Do not interpret a group-page count as the scan window count or a narrow period as a cheap indexed date seek.

## Four directions using the pinned reads

1. **Comparison and trend.** Use two independent bounded `usage.get` walks, same metric, scope, offset and aligned elapsed interval, never a combined 62-day request. Daily views keep Today / 7 / 14 / 31 days; compare like-for-like calendar slots in the captured fixed offset. With a partial last day, end the prior period at the same clock cutoff on its corresponding last day (not at midnight). Show exact absolute change only on exact comparable data, percent only with a positive baseline and percentage points for rates. Explain excluded/missing facts and suppress comparison if either walk is incomplete or its denominator invalid. Mark an observed rise only between adjacent comparable buckets; no alert, anomaly score, or claim of a usual baseline beyond the named previous period. Per-thread sparklines at scale need a different read; do not launch a series per row.
2. **Filters and drill-down.** Thread is a real owner scope (`thread_id`), so it can filter day/hour trends and model breakdown. All-Thread day/hour -> one bounded `group_by=thread` walk over that bucket's intersection with the active interval -> available Conversation link uses existing reads. `group_by=model` over an exact period or picked bucket supplies a model breakdown, not a model-filtered timeline or model-filtered Thread list. A model selection can narrow/highlight already returned model rows only, labeled as such. Core exposes `connection_rates.by_connection` keyed by saved profile, with rate observation/wait counts for the candidate window, not per-connection token attribution; a view of reported rate facts can select a displayed connection, but must not imply it filtered usage. Do not show disabled model/connection scope switches as promised work. Filter and Group by are separate concepts.
3. **Presentation.** Keep Overview, Tokens, Compaction, By Thread and operational navigation. Overview starts with period and scope, one clear primary trend/count with unit and coverage, then compact secondary Stats (for example token totals and cache share) and an exact-values disclosure. Move explanations, source detail and breakdowns below the chart or behind its bucket/row disclosure. A phone stacks controls and one-line rows, limits axis-label density without discarding data, and puts exact long names and values in the detail. Do not force a desktop multi-column number table to be the first screen. Use the existing tokens, chart roles and text, not a new palette; keep the data origin visibly scoped.
4. **New metrics, not new facts.** Report cached input and `cached/input` for comparable covered attempts: input includes cached, use exact non-overlapping parts, do not average page ratios, and do not clamp or turn absent/overflow/inconsistent data into zero. Whole-period share requires complete valid pairs and a positive denominator; otherwise show unavailable/coverage. This is actual reported cache use, not a counterfactual saving, a guaranteed hit, or a discount. For compaction show `trigger.input_tokens` and `post_compaction_input_tokens` only where both are present: an observed signed input change between those requests, not tokens saved by the summary (other context may change). Manual/adopted/null/not-applicable and retained/shared scope stay explicit. Summary requests/usage are separate from conversation; model groups omit summary attribution. Mean/max input per request can use existing known-count/mean and max facts with coverage; do not add page percentiles or pretend requests are turns. Core `usage.get --turn TURN` can report saved per-state totals for one known Turn (also Run/Thread scopes); Studio's typed browser args currently have no `turn_id`. A future single-turn detail can use the existing owner read only after checking the bridge argument/decode path and authoritative Turn identity. Do not divide by guessed turn counts, or scan every Turn to estimate a distribution.

### Rolling 24 hours is not Today

Add **24 hours** next to Today and the existing day presets (7, 14, 31). Capture one `until` instant on entering/changing/refreshing the scope; `since = until - 24 elapsed hours`. Group with `hour` and the same explicit fixed offset used for daily display, held across both walks. Core's key is `YYYY-MM-DDTHH:00:00+09:00` (for example), not the cursor, a browser-rendered locale string, or an elapsed-hour index. Compare with `[since-24h, since)`; align by elapsed offset with identical clipped edge durations. On a non-hour cutoff up to 25 calendar-hour buckets intersect each window (two clipped edges); at an exact bucket boundary there are 24. Label partial bars and expose effective start/end/offset in the value table. If owner-local zones are ever offered, retain the numeric offset and canonical instant to distinguish repeated DST hours; this design only offers the existing fixed offset and does not claim DST-aware local time or arbitrary IANA zones.

All four directions apply: explicit previous 24 hours, hour-to-Thread down to Conversation using clipped hour bounds, fewer visible tick labels with full values on tap, and the same qualified cache/compaction/per-request metrics where reported. Do not treat a display clock hour as a fresh hour-long read beyond the selected interval. No auto-scroll or hidden polling to advance the window.

### Read ownership, refresh and failure

Core owns facts and cursors; Data validates wire identity/shape; Insights owns one period/scope key (bounds, offset, grouping, owner generation), coverage, cancellation and request admission; the screen owns presentation and one selection. At most a current walk, an opt-in previous walk and one opened bucket walk; serialize under existing admission, with per-walk bounds and explicit continuation. The mock counts saved completed, failed and incomplete conversation attempts, not turns or provider receipts. Compare different periods as separate owner reads, never as an atomic multi-period snapshot. No walk per chart. Share a source result between Stats, charts and their value tables. On supported authoritative change hints, mark the affected visible scope for a coalesced re-read using the same admission; a hint is not a delta. Confirm the exact hint coverage before claiming automatic freshness; keep explicit Refresh. Cancel obsolete reads on scope/navigation/owner change, discard late responses, and invalidate expired cursors rather than mixing generations. Keep stable nodes and last accepted data labeled stale during a same-key reread; never show old data as new-scope data. Show loading on the first read for a scope or explicit loading of more, not a page replacement on refresh; partial and retry controls stay beside the affected chart. Empty, reported zero, no recorded bucket, partial, unavailable and overflow are different states.

No chart library by default. Existing CSS/inline SVG and one-line row parts are enough for the first path. Prefer a visible value readout and a native button/link; never require hover, precise SVG hit testing, or a tooltip for activation. Keep keyboard focus/return and the disclosure's `aria-expanded`; with a visual mark, the same action and value must be reachable without the mark, including on touch. Use direct labels, series order/shape or stroke distinctions as well as color, a labeled unit and chart summary, native table headers/caption and full values, no announced hover stream, no color-only missing/selected state. Use token spacing, contrast, aligned tabular numbers, and readable ticks; richness comes from hierarchy and spacing, not decoration. Respect reduced motion; no decorative animation and nothing beyond whole-element transform/opacity per #144. Check EN/JA strings, keyboard, focus, 390 px without horizontal page scroll, zoom, light/dark contrast, and value parity in the later mock. No physical AT result is claimed. A library or a new primitive would require a mock, user approval, a reason, measured bundle cost and a documented bound; no new dependency is proposed.

## Questions for the user: would a new Core read be worth it?

Not a plan or a Core issue. Existing reads suffice for the first mock path. If the user later approves exploring a gap, ask which one is worth a separate Core issue and bounded contract:

- **True model/connection usage filters**: should grouped usage accept exact saved model and/or saved connection/profile IDs and combine them with the existing optional Thread scope, before hour/day/Thread grouping? Can Core report unassigned/legacy IDs and summary attribution separately rather than pretending the same filters apply to summaries?
- **Ranked trends / cross-Thread per-turn distributions**: is a bounded multi-key time-by-Thread read, or a bounded period turn-group/distribution read with validated Turn refs and coverage, useful enough? Today a single known Turn is readable; hourly/daily groups and Thread ranks cannot be joined to recover it. Exact joined conversation-at-bucket navigation would need a bounded mapping from activity/attempt identity to a visible conversation anchor if opening the Thread is insufficient.
- **Summary savings**: is an owner-backed matched measurement of what changed (same attributable input basis, adoption and later attempt identities, coverage) worth separately specifying? Without a defensible measured comparator, keep observed before/after only; do not ask Core to synthesize a counterfactual.
- **Longer baselines**: is a bounded reference distribution with defined cohort/coverage worth pursuing if previous-period comparisons do not answer “usual”? Do not scan unbounded history or manufacture a norm.
